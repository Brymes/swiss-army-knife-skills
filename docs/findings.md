# Findings, coverage and reports

This page defines the run artifacts that carry a claim from raw observation to a report:
`findings.json` (verdicts and evidence), `coverage-ledger.json` (what was and was not
tested) and `run-metadata.json` (revision, scope and configuration). The JSON Schemas live
in `schemas/`; the code lives in `src/sak/findings.py` and `src/sak/report.py`.

The verdict vocabulary — `confirmed`, `needs_validation`, `rejected` — follows the
Cloudflare [`security-audit`](https://github.com/cloudflare/security-audit-skill) skill,
which is MIT licensed and vendored separately. Only the three verdict names are reused; no
upstream schema text or code is copied here.

## Run directory

```text
runs/<run-id>/
  run-metadata.json      # schema_version, run_id, started_at, target, revision, budget
  state.json             # best-effort alias when run-metadata.json is absent
  findings.json          # findings and the cumulative dedupe log
  coverage-ledger.json   # trust boundaries, probes, evidence, gaps
  evidence/              # immutable observation files referenced by hash
  logs/
  REPORT.md              # generated by `sak report`
  FINDINGS-DETAIL.md
  NEEDS-VALIDATION.md
```

Run directories are ignored by git (`runs/*`); a durable demo run belongs to the integration
task, not to a worker's scratch tree.

## Finding records

Every finding has one verdict, five fingerprint fields and evidence metadata:

| Field | Meaning |
|---|---|
| `id` | Stable record id, `F-...` |
| `title`, `description`, `impact`, `remediation` | Human claim and fix |
| `status` | `confirmed`, `needs_validation` or `rejected` |
| `severity` | `info`, `low`, `medium`, `high` or `critical` |
| `asset` | Host, URL origin, repository or binary under test |
| `entrypoint` | Route, handler, function or command that reaches the boundary |
| `root_cause` | Short class of the weakness, for example `sql-injection` |
| `principal` | Account or role that exercises the entrypoint |
| `resource` | Object, table, file or state affected |
| `fingerprint` | SHA-256 over the five fields above (see below) |
| `evidence` | Evidence records: `id`, `kind`, `path`, `sha256`, `timestamp`, `producer` |
| `open_question`, `next_action` | Required for `needs_validation` |
| `reason` | Required for `rejected` |
| `status_history` | Ordered `from`/`to`/`at`/`actor`/`reason` transitions |

The schema also carries `cwe`, `source` (`tool`, `prompt`, `adapter`, `engine`, `model`),
`tags` and `notes`.

### Verdict rules

| Verdict | Requirement |
|---|---|
| `confirmed` | At least one evidence record. A confirmed claim without evidence is a schema error, not a warning. |
| `needs_validation` | An open question **and** a next action. This is an honest lead, not recall or coverage. |
| `rejected` | A reason. The record stays in the file so the negative result is not lost. |

### Status transitions

```text
needs_validation -> confirmed | rejected
confirmed        -> needs_validation | rejected
rejected         -> confirmed | needs_validation
```

Each transition appends a `status_history` entry with the actor and optional reason.
Transitioning to the same status is an idempotent field update and does not add history.
`confirmed` is refused when the record has no evidence; `needs_validation` is refused
without both fields; `rejected` is refused without a reason. Downgrading a confirmed record
is allowed and expected when a verifier disproves it.

Validation also checks that history is contiguous (`from` equals the previous `to`) and
that its last entry matches the current status.

## Fingerprint and dedupe

```text
fingerprint = SHA-256(JSON([
  normalise_asset(asset),
  collapse_ws(entrypoint),
  casefold(collapse_ws(root_cause)),
  collapse_ws(principal),
  collapse_ws(resource)
]))
```

`normalise_asset` lowercases only the URL scheme and authority. Every other
component is normalised by whitespace collapse alone. URL paths, query strings,
entrypoints, principals and resources keep their case because they are opaque,
case-sensitive identities: `AccountA` and `accounta`, or `ItemA` and `itema`,
must not collapse into one root cause. The root-cause slug is the only
semantic field whose case is folded.

Wording, severity, tool, evidence and status are deliberately excluded: two tools that
observe the same root cause collapse onto one record. Changing the principal, resource,
entrypoint or root cause changes the fingerprint.

`sak findings dedupe` groups records by fingerprint and keeps the strongest verdict
(`confirmed` > `needs_validation` > `rejected`, then earliest `created_at`). The kept record
unions evidence and tags, fills missing narrative fields from the other records, and takes
the earliest creation and latest update time. Every collapsed record is appended to the
top-level `dedupe` log with its id, title and status, which is what makes the report's
before/after table possible. Dedupe is idempotent: a second pass finds nothing to collapse
and adds no log entry.

`sak findings add` uses the same rule when merging into an existing file, so importing three
scanner reports does not create three copies of one issue. The log records the merge as
`merged on add`.

## Evidence

Every evidence record carries:

| Field | Meaning |
|---|---|
| `id` | `E-...`, unique within the run |
| `kind` | `request`, `response`, `command`, `log`, `source`, `observed`, `screenshot`, `other` |
| `path` | File path, relative to the run directory by convention |
| `sha256` | Hash of the observed file |
| `timestamp` | When the observation was made |
| `producer` | Tool, adapter, prompt or person that produced it |

`sak findings validate` checks that each referenced file exists and that its hash still
matches. A changed file is a validation failure and a report integrity warning: evidence is
immutable in substance, so a later interpretation may change the verdict but must not rewrite
the observation. `sak findings add` fills missing evidence metadata from the file on disk.

Evidence text is never rewritten by masking. Masking happens at display and report time so
the stored observation stays reproducible.

## Coverage ledger

The ledger enumerates trust boundaries and their probes:

```json
{
  "id": "TB-01",
  "name": "Login handler to database",
  "status": "covered",
  "probes": [
    {
      "id": "P-01",
      "description": "Login with fixture credentials and a quote payload",
      "executed": true,
      "evidence": [{ "id": "E-login", "kind": "log", "path": "evidence/login.txt",
                    "sha256": "…", "timestamp": "…", "producer": "curl" }]
    }
  ]
}
```

Rules:

- A boundary is **covered** only when at least one probe has `executed: true` and all of
  its evidence records are present and hash-verified. A planned probe is not coverage, and
  an executed probe with missing or tampered evidence is rendered as **unverified**, not
  covered.
- An **excluded** boundary must record a `gap`; scope exclusions count as uncovered and are
  listed as gaps rather than silently removed.
- Boundary `status` is derived from probes. A hand-edited status that contradicts them is a
  validation error. `refresh_ledger` recomputes it.
- Merge matches boundaries by `id` and probes by `id`. An executed probe is never downgraded
  by a later planned record; evidence arrays are unioned; an exclusion survives a
  planned-only update; the merged status is recomputed.
- `ledger_gaps` lists every boundary without coverage, with the recorded reason or a default
  (`planned but no probe executed` / `excluded from scope`).

`sak report` prints the covered/total count, a per-boundary table and an explicit
`Unresolved coverage gaps` section.

## Reports

`sak report RUN_DIR` writes three files into the run directory:

- **`REPORT.md`** — run scope and revision, summary counts, a **before/after dedupe** table
  (candidate records, each verdict, distinct fingerprints, duplicates removed), confirmed,
  needs-validation and rejected tables with evidence links, coverage and gaps, evidence
  integrity and artifact presence.
- **`FINDINGS-DETAIL.md`** — every record with its full fingerprint, fields, evidence hashes,
  status history and source.
- **`NEEDS-VALIDATION.md`** — open question, next action and evidence for each unresolved
  lead. These records never count as recall or coverage.

The report is strict about malformed findings and metadata: a schema or semantic error stops
the render with the offending path and message. Wrong-type nested shapes such as a numeric
`status_history`, a mapping in place of an evidence list, or a non-string probe id return
structured validation issues instead of raising `TypeError`. Missing optional artifacts
produce explicit warnings instead, so an incomplete run is visible rather than silently clean.

A `confirmed` record counts only when all of its evidence records are present and hash-verified.
Otherwise the report keeps the source record unchanged but moves it to **Confirmed claims
excluded from counts** and lists it in `NEEDS-VALIDATION.md` as blocked by evidence. The same
rule applies to coverage: an executed probe with invalid evidence is shown as `unverified`
and counted as an unresolved gap, not as verified coverage. The summaries therefore never
claim a confirmed issue or a covered boundary that the evidence cannot support.

Secrets are masked in every rendered file: authorization headers, cookies, bearer/basic
tokens, `token=`/`password=`-style assignments, and obvious AWS, GitHub, Slack and private-key
formats become `***`. Masking is presentation only and never writes back to the evidence.

## CLI

`src/sak/findings.py` and `src/sak/report.py` each export
`add_parser(subparsers)`. The root `sak` dispatcher in `src/sak/__main__.py` is owned by
T1 and must call those two exports before the commands below are reachable from the
installed `sak` script; that wiring is tracked as R-T1-006. The modules and their handlers
are fully testable without the root dispatcher.

```sh
sak findings validate runs/demo/findings.json
sak findings list runs/demo/findings.json --status confirmed --json
sak findings dedupe runs/demo/findings.json --write
sak findings add candidate.json --run-dir runs/demo
printf '%s' "$FINDING_JSON" | sak findings add - --run-dir runs/demo
sak findings status F-002 confirmed --run-dir runs/demo --actor verifier \
  --evidence evidence/browser.txt --reason "Control reproduced execution"
sak report runs/demo
```

`validate`, `list` and `dedupe` accept a JSON or YAML findings document. `add` accepts one
finding or a findings document from a file or stdin and merges by fingerprint. Every command
supports `--json`. Validation errors name the record, the JSON path and the fix; the process
exits non-zero.

## Limits

- The fingerprint is intentionally coarse. Two distinct vulnerabilities in the same
  entrypoint with the same root cause and resource collapse; split them by a narrower
  `root_cause` or `resource` if they need separate records.
- A hash proves the evidence file did not change, not that the observation supports the
  claim. A verifier still has to review it.
- The report does not compute eval metrics (recall, precision, cost); the evaluation harness
  reads these artifacts and does that separately.
